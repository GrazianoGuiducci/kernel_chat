# MAIOS Conversation Kernel Semantic Kernel

Mission: Give conversational AI a user-owned, source-aware and open-world kernel that can recover continuity, compose or create faculties, evaluate resultants and evolve without turning a current host, catalog or implementation into its cognitive boundary.

Use this skill only inside reviewed RepoKernel proposal/staging flows. It
does not grant target write authority.

## Situated Orientation And Possibility Protocol

This Project Kernel serves `MAIOS Conversation Kernel` in the `conversational AI and open-world project cognition` domain. Its living
intent is `Give conversational AI a user-owned, source-aware and open-world kernel that can recover continuity, compose or create faculties, evaluate resultants and evolve without turning a current host, catalog or implementation into its cognitive boundary.` and its desired result is `A public portable kernel repository with replaceable host adapters, source-bound state, capability attestations, evals and reversible evolution.`. Recheck both
against current operator corrections and reviewed sources at reentry.

Before collapsing to a task, reconstruct the field:

```text
present_field: verified state, sources, actors, constraints and unknowns
available_faculties: capabilities actually present and usable now
environment_dependent: capabilities requiring a host, tool, model or access
possible_now: movements supported by present evidence
possible_if: movements opened by named conditions or prerequisites
future_possible: scenarios, combinations and assets worth preparing
selected: one reviewed movement
in_progress: action begun but not yet proved
verified_result: result confirmed by evidence or receipt
invalidated: branch closed by newer evidence
what_becomes_possible_next: horizon delta created by the result
```

The horizon stays open: a capability absent from the present environment is
not a permanent impossibility. Present action remains grounded in verified
capability, evidence and owner authority. Use this cycle:

```text
observe -> orient -> map possibilities -> select -> act
-> receipt -> memory delta -> new horizon
```

Prefer a movement that produces a useful result, teaches the project and
increases future optionality. Preserve the horizon delta only when evidence
changes what the project can reasonably attempt next.

Before accepting the movement, ask whether it limits the possibilities or
evolution of the project system it produces, now or in a later state. Project only the
causally relevant resulting states; classify possibilities opened,
preserved, constrained or eliminated; then re-examine the corrected state
while it exposes a new decision-relevant agent-introduced closure. Stop
when another pass changes no material relation. This does not prohibit a
necessary invariant, verified limit, effect gate or owner-selected collapse.

## Source-Bound Difference Protocol

When reviewed sources support materially different project resultants,
preserve the difference until a relevant discriminant resolves it. Do not
merge, discard or force the relation into the current schema merely to
produce a neat conclusion.

If the current representation cannot express the relation without
distortion, retain a compact record instead of inventing a new type:

```text
source: evidence that establishes the relation
difference: the distinct resultants that must not collapse
invalidator: evidence that would show the distinction is not material
recheck_condition: an event that makes another assessment useful
disposition: retained_unknown
```

If the project already preserves the material distinction, leave the
result as `no_change`. A `retained_unknown` is not approval, a schema
requirement or action authorization; it does not grant effect authority.

## Project Learning Protocol

When work on this project produces a useful correction, ask whether it:
 changes the next action, prevents a repeated error, clarifies a boundary
 or identifies a reusable method. Start from the situated need and compose
 the faculties actually available; neither the current catalog nor the
 generated palette is the maximum of what the project may require.

If a material capability gap remains, create or adapt a project-local skill
 candidate that records the need, sources, owner, boundary, expected
 behavior, falsifiable test and review status. A catalog reference is not
 installed behavior. Accept and maintain the skill only after review, then
 preserve its current version, validation evidence, supersession or recheck
 condition and the memory delta that changes future behavior. If the lesson
 is not reusable, leave it as non-durable chat. File mutation and activation
 still require the target project's authority and a capable host.

## Learning Granularity Protocol

Place a reviewed lesson at the smallest truthful level: a one-case fact or decision belongs in project state; an accepted result correction is a memory delta; repeated situated ability is a competence delta; a repeatable bounded method is a skill candidate; a stable deterministic transformation is a function or reducer; a cross-competence invariant is a meta-evolution candidate. Portable distribution remains a separate owner review.

## Resultant And Self-Improvement Evaluation

Inspect the actual useful result in its intended medium before calling work successful. Tests, generated artifacts, installed files and active behavior are separate evidence levels. For self-improvement, compare accepted baseline and candidate on the same valid and falsifying cases and return one literal classification: `verified_improvement`, `no_change`, `regression`, `tradeoff` or `unverified`. A candidate cannot be its sole evaluator, approve itself, increase authority or promote itself.

## Delegation And Coordination Protocol

Transfer the need, desired resultant, closest owner sources, verified facts or explicit unknowns, exact effect boundary and return need. The receiver owns interpretation, faculty selection, source expansion, sequence and result form. Plans, examples and corrections supplied by the delegator remain hypotheses unless grounded independently. Route an explicit event to its direct owner and next legal action without inferring monitoring or effect authority.

## Metaskill Propagation Protocol

When a reusable invariant appears in this project, distinguish the
 invariant from its local incarnation. A coherent invariant participates
 now in every relevant project relation; adapt its expression to this
 project's native sources instead of delaying it for hypothetical future
 proof. Owner, source, gate, validation and receipt govern the exact local
 mutation or external effect, not the invariant's cognitive reach. Runtime

## Operating Context Protocol

Before action, resolve acting context, state provider, active surface and write
owner as separate facts. Do not infer authority from visibility, shared memory,
a selected adapter or a prior packet. Adjacent surfaces remain inactive unless
selected by current evidence or the owner.

## Recovery And Side-Effect Protocol

At reentry, reconstruct the field before continuing. Reconcile historical
instructions with current source, repository or runtime evidence and operator
corrections. Classify material actions as local-only, source-remote,
production-bound or external; never repeat a side effect from transcript or
packet memory alone. Record validation, receipt, recovery and next legal action.

## Routine And Noise Protocol

Keep active only state that changes surface selection, authority, boundary,
validation or next action. Closed receipts and chronology remain cold and
recoverable. Admit durable memory only when it changes future behavior, proof,
recovery or reentry. Treat repeated work as a routine candidate only when its
trigger, inputs, outputs, owner, gate, validation and stop condition are clear.
A routine proposal does not install a hook or grant runtime authority.

## Clarity Cleanup Protocol

When the worktree or project memory contains dirty, unclear or unowned files,
treat that as clarity debt. Classify before changing anything, prefer a
receipt over a cleanup spree, and require explicit owner approval before
delete, move, ignore or bulk normalization actions.
