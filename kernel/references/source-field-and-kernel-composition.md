# Form a source field and compose independent kernels

This knowledge deepens [Core source-field formation](../KERNEL.md#kernel-chat-source-field)
and [Competence composition](../COMPETENCE.md#movement-through-the-competence-field).
It becomes pertinent when the distribution of sources, owners or receivers
changes what can be understood, combined or continued.

## Understand the topology that serves the work

A persistent surface can carry more than files. Separating, sharing, linking
or hiding knowledge changes what a receiver can perceive and compose. Use the
present purpose and its knowledge owners to understand which relations must
remain together, which must stay independent and what each receiver can reach.

Distinguish entity, name, role, interface, provider, filesystem and project.
The same directory can contain several owners. Two checkouts with a similar
name can carry different revisions or specializations. A different interface
can reach the same source without becoming a new owner.

Find the canonical source, useful local learning, configured projections,
private material and shared knowledge where those distinctions change work.
The selected persistence surface owns its actual continuation; its location
does not grant authority over adjacent sources.

For example, a guide lives in one repository while several receivers use it.
Keep the living method with its owner and give each receiver a pertinent
entry and enough reason to recover it. A copied summary that no longer reaches
the method can lose its practical depth. Conversely, one shared source can
need distinct local interpretations because the receivers have different means.

## Make useful depth reachable selectively

Keep these relations distinct:

```text
source exists
!= reachable by this receiver
!= discoverable when pertinent
!= selected into this working context
!= understood or exercised
!= assimilated in later work
```

Choose actual source paths and native access means from those needs. A
repository, knowledge space, filesystem, connector graph or another adequate
carrier can support the relation. Git is not required by the semantic method.
Do not load every source merely to make the field appear complete.

Reachability can change which competences become recognizable, not only where
their files are stored. If the initial question is selecting every source and
excluding unfamiliar contributions, use the
[formation method's complementary orientation](formation-and-inheritance.md#let-the-reachable-field-change-pertinence).
Let the resulting knowledge change the question or the selection criterion,
then preserve the useful source connection in its actual owner.

When a source becomes material, resolve its actual identity and current owner.
An old checkout can remain useful history without representing the latest
source. An unreachable pointer leaves that relation uncertain; it does not
prove that the knowledge or capacity is absent. Follow only the depth that
can change the result.

Revisit the distribution when new work changes access, ownership, privacy,
concurrency or the place where learning must continue. Preserve valid local
specialization and provenance. Moving or replacing material is an exact effect
with its own owner; understanding the topology does not perform that effect.

## Compose kernels by their contribution

A kernel can be useful independently and also contribute inside a common
receiving environment. Understand what each should carry. One sufficient
kernel, a complementary composition, a deepened owner or another kernel left
cold are all possible results. Availability does not select a stack.

For each material contribution retain enough identity, canonical source,
native entry, continuing state and learning destination to understand it.
The environment supplies actual access, tools and coordination. It is not
automatically the semantic owner, and one source's arrival channel does not
own the subsequent domain work.

For example, a domain kernel interprets technical requests while a general
kernel supports continuity and formation. If both help the present work,
compose those functions. Domain knowledge returns to the domain owner;
a better formation method returns to its owner; a failed connector concerns
the receiving mechanism. If the domain kernel is already sufficient, another
general kernel need not become its dependency.

Preserve each kernel's source, local evolution, state, authority and proof.
Shared knowledge does not merge host observations. A useful semantic
contribution is not necessarily delegation to a second executor. Creating an
agent, calling a provider or changing a job requires that actual selected
effect and its means.

## Continue a shared result without merging owners

A combined result can change several competences. Return only the reusable
difference that changes each owner's next work, with enough reason and source
to make it understandable. A shared file is not a notification or proof that
another receiver read it.

Before a concurrent write, recover the current object and reconcile the actual
contribution. Use a revision check, coordinated write or another native means
when that protects the selected effect. A worktree or local file lock does
not establish universal writer serialization or a semantic merge.

An inventory or interoperation profile can help when a real environment needs
it. Form that mechanism from the observed receiving relation rather than
requiring a registry, manifest or central broker for all kernels. The useful
composition retains independent learning and can simplify or dissolve when
the present work no longer needs it.
